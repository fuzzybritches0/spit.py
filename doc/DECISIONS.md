# DECISIONS.md - Design Decision Log

Append-only log of the design decisions taken during spit.py tool development,
extracted from `~/TOOL_IMPLEMENTATION_SUMMARY.md` (decisions 1-58) plus the
implementation notes that accompany them. New decisions continue the numbering.
Short version in task/spec docs always points here.

Why append-only: several entries deliberately *reverse* earlier ones (33/34
reverse parts of 24's era; 45 amends 32). The history of why a rule exists is
what stops a future agent from "improving" a deliberate asymmetry away - e.g.
the terminator-policy difference between `delete_lines` and `patch`/`insert_line`
(40 vs 45/52) or the ignored patch header counts (33/54).

## Key design decisions (verbatim)

1. **Extended `write_file`** instead of creating separate `append_file` tool
2. **`prepend_newline=True`** by default for append operations
3. **`grep` uses regex** patterns (more powerful)
4. **`find_files` uses glob** patterns (simpler, shell-style)
5. **Default `recursive=True`** for both tools (most searches need subdirectories)
6. **Default `max_results=100`** to prevent overwhelming output
7. **Renamed `read_file` to `read_files`** to support multiple files
8. **`list_directory` enhanced** with owner/group and file type detection
9. **Markdown table output** for `list_directory` (better rendering in chat)
10. **Symlink detection with full paths** for better context
11. **Created `file_info`** for single file metadata (complements `list_directory`)
12. **`file_info` supports JSON output** for programmatic use
13. **De-duplicated code** between `file_info` and `list_directory` (shared metadata functions)
14. **`search_replace` supports both plain text and regex** patterns
15. **`search_replace` preview removed** — LLMs handle replacements reliably; dry_run shows counts only to save tokens
16. **`terminal` uses tmux** (via `libtmux`) for persistent interactive sessions — one tmux session per chat conversation
17. **`terminal` is sandboxed by default** using `bwrap` (bubblewrap); each window runs a bash shell inside the sandbox
18. **`terminal` screen is 24×80 with no scrollback** — only the current screen is captured; cursor position is shown via `█`
19. **`lsterm` shows only live sessions** — dead sessions are auto-cleaned so their names can be freely reused
20. **Terminal tools use a different file structure** — no `scripts/` subdirectory; they interact directly with the `Run` class's tmux methods
21. **`diff` uses `difflib` from the stdlib** — no external dependencies; lines passed with `keepends=True` because difflib only appends line terminators to header lines
22. **`diff` supports three output formats** (`unified`, `context`, `side_by_side`) plus a change summary (added/removed/changed counts); identical files short-circuit to a single line
23. **`diff` exits non-zero only on errors** (missing file, not a file, bad format) — a plain difference is not an error
24. **`patch` parses unified diff natively (stdlib only)** — no external patch library; a small state machine handles `---`/`+++` file headers, `@@` hunks (including abbreviated ones without counts), `\ No newline at end of file` markers, and empty lines as hunk separators. The `^^` trailing-header pre-pass that used to run in front of it is gone — see 34 and 54
25. **`patch`'s `diff` argument is polymorphic** — it accepts either the patch content or a path to a patch file; an existing file path is auto-detected via `Path(diff).is_file()`
26. **`patch` auto-strips markdown code fences** — patch content pasted straight from the `diff` tool output (wrapped in ```` ``` ````) works without cleanup
27. **`patch` places a hunk if and only if the place is unambiguous** — one match of the body wins whatever the header claims (so a stale header on a shifted file still works); several matches let the header's start line pick the nearest; an equidistant tie is **refused** rather than resolved to the earlier match as `patch(1)` does — guessing a location and reporting success is the worst kind of leniency; no match fails with an expected-vs-found diagnostic naming the culprit line. See 53
28. **`patch` has `dry_run`** (consistent with all destructive tools) — it renders a unified diff preview via `difflib` and writes nothing
29. **`read_files` line numbering is opt-in** (`show_line_numbers`, default `False` → byte-identical legacy output), `cat -n` style (right-aligned number + tab, width scales with digit count), built on `splitlines()` so LF/CRLF/lone-CR count uniformly and trailing-newline files produce no phantom line; CRLF files are *displayed* with LF endings in numbered mode (display only — `keepends=True` was rejected because a trailing `\r` corrupts terminal rendering)
30. **`insert_line` has two equivalent position modes** — `line_number` (insert *before* line N, default 1) and `after_line` (insert *after* line N, 0 = beginning); they are mutually exclusive (providing both with a non-default `line_number` errors out) to avoid ambiguity
31. **`insert_line` appends via `line_number = n+1` / `after_line = n`** — no separate "append" mode; out-of-range positions error with the valid range in the message
32. **`insert_line` `dry_run` reuses the `patch` dry_run convention** — a real unified diff (via `difflib`) of the would-be change, so the preview is pasteable straight into the `patch` tool; the original file's trailing-newline state is preserved byte-exactly, both by the applied write and (since the `insert-line-preview-markers` branch) by the preview's `\ No newline at end of file` markers — see 44
33. **`patch` ignores the header's line counts** (reversed on `patch-tool-fixes-2`; was: strict, a mismatch a hard error) — the counts are derivable from the body, so demanding them asks the model for arithmetic that carries no information and refuses a perfectly unambiguous patch for getting it wrong. They are still *matched* by the regex, so both `-N` and `-N,M` spellings parse, but they are never captured and no logic reads them. See 54
34. **`patch` headers are optional per hunk and may be mixed** (reversed on `patch-tool-fixes-2`; was: all-or-nothing) — the rule existed only to catch "forgot a header on one hunk", but under the unambiguity rule a missing header costs nothing: the body either matches uniquely or it does not. Refusing a patch whose two hunks each match in exactly one place was strictness with no payoff. See 53
35. **`patch` is atomic** — any failing hunk (empty hunk, no hunks, no match, ambiguity, overlap) rejects the whole patch with a precise `ERROR:` and the file left unmodified; a headerless pure-insertion hunk (no old lines to anchor) is always ambiguous; nothing is ever applied partially
36. **`patch` preserves the file's line endings** — the file is read with `newline=''` and the dominant terminator (LF / CRLF / lone CR, from the first line break) is reused in the join and the write, so patching a CRLF file no longer silently converts the whole file to LF; the file is written with `newline=''` so Python never re-translates the endings
37. **`patch` tells a real file header apart from a `--`/`++` body line by pairing** — a header is a `--- old` line *immediately followed by* a `+++ new` line (exactly how `diff`/`git` emit them); a lone `---x`/`+++x` body line is content, not a header. The old code skipped any line whose first three chars were `---`/`+++` when outside a hunk, so a headerless patch whose first body line removed a `--`/`++` line was silently dropped while still reporting success; pairing fixes this . The same pair test used to guard the `^^` body-run walk as well; that walk is gone (decision 54), and pairing is now only what tells a file header apart from a body line — see *Next steps → 4* for the one shape it still cannot tell apart
38. **`patch`'s no-match error names the real culprit line** — it scans the expected block against the file and reports the first differing line (`line N: expected \`x\`, found \`y\``, or `<past end of file>`), because the old message printed only `exp[0]` vs `work[hint]`, which were frequently identical (the true mismatch was a later line), giving the LLM no actionable information. A blank line in the mismatch is now spelled `a BLANK line` rather than appearing as an empty gap between two backticks, and the message carries the remedy with it (` ` for context, `+`/`-` for added/removed, an empty line only separates hunks) — see 57
39. **`delete_lines` composes its two filters instead of making them exclusive** — `start_line`/`end_line` select the region and `pattern` selects the lines inside it (`pattern` alone means the whole file); at least one of the two is required. They are filters, not two spellings of the same position, so unlike `insert_line`'s `line_number`/`after_line` (mutually exclusive because they conflict) combining them is meaningful: "delete the TODO lines between lines 100 and 120".
40. **`delete_lines` keeps every line's own terminator** — the file is read `splitlines(keepends=True)` and the kept lines are joined verbatim, so LF/CRLF/lone-CR and the trailing-newline state survive with no dominant-terminator detection at all (a deletion removes whole lines, it never has to invent an ending). Consequence for a file whose last line is unterminated: deleting that line leaves the previous line's newline behind (`a\nb` → delete line 2 → `a\n`), which is POSIX / `sed '2d'` semantics.
41. **`delete_lines`: `end_line` without `start_line` is an error, not "from the top of the file"** — defaulting the start of a destructive range to line 1 is the wrong kind of leniency; the error names the missing argument.
42. **A `delete_lines` pattern that matches nothing is not an error** (exit 0, `No lines matched`) — consistent with `grep`/`search_replace`/`diff`; only malformed input (nothing specified, empty or invalid regex, bad range, missing file) exits non-zero, and the file is never touched on error.
43. **`delete_lines`'s `pattern` is regex-only** (like `grep`), with no `use_regex` toggle — `search_replace` needs the toggle because exact-text replacement is the common case, whereas "delete the lines that look like this" is inherently a pattern job; matching is `re.search` per line after stripping the terminator (so `$` is not fooled by the newline) and the description tells the model to anchor with `^`/`$`.
44. **Dry-run previews that must round-trip through `patch` have to write `\ No newline at end of file` markers by hand** — `difflib.unified_diff` never emits them, so a preview of a file without a trailing newline silently gains one when it is pasted into `patch`. Both `delete_lines` and `insert_line` terminate any body chunk that carries no terminator and follow it with the marker line (one marker per affected last line, exactly like real `diff`/`git diff`). `insert_line` had the same flaw — found while building `delete_lines`, fixed on the `insert-line-preview-markers` branch, where 8 of the new checks fail against the old script.
45. **`insert_line` keeps the file's line endings** (the open issue 44 surfaced, fixed on the `insert-line-line-ending` branch): it used `read_text()` (universal newlines) and `"\n".join()`, so any CRLF or lone-CR file came back entirely LF — and its own preview, applied by `patch`, came back with the endings intact, so the two routes disagreed byte-wise (`one\r\ntwo\r\n` + `MID` → `one\nMID\ntwo\n` vs `one\r\nMID\r\ntwo\r\n`). It now reads/writes with `newline=''` and joins with the terminator of the file's first line break, i.e. exactly `patch`'s rule, so an insert performed directly and the same insert performed by pasting its preview into `patch` yield the same bytes for LF, CRLF, lone-CR, mixed and unterminated files.
46. **The line-ending rule lives in one file: `spit_app/tools/scripts/common/lines.py`** — `detect_newline()`, `ends_with_newline()`, `strip_newline()` and the `newline=''` read/write pair, extracted verbatim from `patch` (which lost its private copy), used by `insert_line` and — since the `delete-lines-shared-line-helpers` branch — by `delete_lines`, whose private `strip_ending()` and private `newline=''` read/write pair are gone. Tools must not disagree about what a file's terminator is, so there is one definition; `common/file.py` (stat metadata for `file_info`/`list_directory`) was the precedent. Because the sandbox receives one concatenated script, shared code is *prepended* by `get_script(__file__, "lines")` — a tool script can never import another tool script. The test harness mirrors this: `setup.json` may carry a `"common"` key naming the shared script, and `harness.py` prepends it the same way `get_script` does (without it, a migrated tool's tests die with `NameError`).
47. **Test fixtures are generated, never committed** — a `git format-patch`/`git am` round trip had silently rewritten every CRLF fixture to LF (`git am` treats CR at line end as trailing whitespace and "fixes" it; `core.autocrlf` was unset and there is no `.gitattributes`, so the damage was in the *commits*, not the checkout). The byte comparisons then passed **vacuously** — both sides normalized identically — and only the two checks whose expectation was a number typed in the test (`grep -c $'\r'`) noticed. `.gitattributes` was rejected: it papers over the checkout half, is invisible in the test code, and one missed pattern means silent coverage loss again. So `fixtures_common.sh` provides `testfile`/`testfile_bytes` (`printf '%b'`: `\n`, `\r`, `\t`, `\0nnn`; double a literal backslash; `\c` would stop output), each suite gets a declarative `create_fixtures.sh`, and `run_tests.sh` creates the corpus up front and `remove_fixtures` on exit (`KEEP_FIXTURES=1` to inspect). Generated corpus verified byte-for-byte against the pre-migration blobs: 73 identical, 12 repaired, 0 unexpected.
48. **Terminator expectations must not come from a file alone** — `assert_cr_lines` / `assert_no_cr` / `assert_last_byte` in `test_common.sh`, plus a `fixtures_selftest` CRLF probe at the top of every `create_fixtures.sh`, so a broken generator cannot quietly make both sides of a comparison agree again.
49. **Every fixture is named after the test that owns it** — `fixtures/tNN-<short-name>.txt`, scratch files and must-not-exist paths included (`t01-work.txt`, `t11-no-such-file`), with `fixtures/shared-<name>` for what several tests genuinely read and `fixtures/corpus/<name>` for `patch`'s six-file corpus (35 references). Semantic names were not a style problem but a correctness one: with `original.txt` / `exp_insert3.txt` a test could compare its output against another test's expectation and pass, which happened twice in one session. The name is now the ownership claim, so the mistake is structural — a test reading test 1's fixture cannot be what test 18 asks for by accident. `create_fixtures.sh` is in test order and stays purely declarative (`testfile` lines only); a derived expectation is generated inside the test that uses it, not in the prologue. See *Next steps → 1* for the full convention and the invariant to re-check after editing a suite.
50. **A rename is verified by content, not by the suite being green** — green tests only prove the renamed paths still resolve; the fixture bytes could have been silently rewritten by the edit. The rename generated both corpora (`git show main:.../create_fixtures.sh` vs the branch's) and compared sorted md5 multisets per suite, and required `git diff main..HEAD` on `run_tests.sh` to touch fixture paths and nothing else. The one allowed difference had to be stated out loud: `delete_lines` lost the never-referenced `empty.txt`.
51. **A fixture no test reads is deleted, not renamed** — `delete_lines`'s `fixtures/empty.txt` matched nothing in `run_tests.sh` (test 16 makes its own empty file with `: >`). Keeping it would have kept a name that looks owned by nobody, which is exactly the ambiguity the naming convention removes; the dead file is reported in the commit message and in *Next steps → 1* rather than quietly dropped.
52. **The line-ending primitives have no private copies left** (branch `delete-lines-shared-line-helpers`) — `delete_lines` deleted its `strip_ending()` and calls `strip_newline()`, and its `read_lines()`/`write_lines()` now delegate to `read_text_raw()`/`write_text_raw()` instead of opening the file themselves; the two wrappers stay because they name the intent (whole-line read, whole-line write) while the shared file owns the mechanism (`newline=''`, utf-8). The private and shared versions tried the terminators in a different order (`"\r\n", "\n", "\r"` vs `"\r\n", "\r", "\n"`), which cannot matter — only CRLF ends in both and both try it first — so this is a pure dedup, proven by the untouched 127 checks rather than by argument. What was deliberately *not* touched is the policy: `delete_lines` still keeps every remaining line's own terminator and does no terminator detection (see 40 and *Next steps → 2*), while `patch`/`insert_line` normalise to the first line break (see 45). Same module, different rules, because the operations differ.
53. **`patch`: the body is the ground truth, the header is a tie-breaker** — one sentence the whole tool now derives its behaviour from, and it draws the line where the model's actual strengths are: strict about *where* an edit lands (never guess, refuse and say what to fix), loose about *bookkeeping* the body already determines (counts, whether a header is present at all, whether hunks are listed in order). It replaced five positioning branches with one `resolve_position()` and deleted the running `offset` that used to reinterpret headers mid-patch.
54. **Dropping `^^` and ignoring the counts are one decision, not two** — the `^^ -1,4 +1,4 ^^` trailing header existed purely so a model could write the counts *after* the body, where they are easy to count. Its cost was ~25 lines of the trickiest code in the tool: a right-to-left pre-pass walking back over each body run, deciding whether an `@@` header was already there, replacing it, and keeping not-yet-moved `^^` lines separating adjacent runs. In practice no model ever used it. Once the counts are ignored there is nothing to write afterwards, so the notation has no purpose and the `@@` form stops being a trap. Removing both was 78 lines deleted, 1 changed, and a differential proof that all 20 non-caret fixtures still produce byte-identical output.
55. **`patch` matches every hunk against the pre-patch file and applies bottom-up** — a hunk's own lines describe the file before the patch, which is what a unified diff means. The old code applied hunks one at a time to a buffer it kept mutating and repaired the headers with a running `offset`, because `@@ -13,... @@` names a line of the *original*; for a headerless hunk, whose `old_start` is a placeholder, that arithmetic is meaningless (t15's headerless hunk shifted the next hunk's hint from line 1 to line 6, rescued only because the match was unique). Matching against the original deletes the offset bookkeeping, makes a hunk immune to text an earlier hunk invented, and needs no adjustment during application at all.
56. **`patch` rejects overlapping hunks explicitly** — the hazard step 55 opens: two hunks that each match the pristine file but claim some of the same lines would each resolve cleanly and the second would clobber part of the first. `main` accepted exactly such a patch, rc 0, returning the plausible-looking union of both hunks with no indication they had both claimed line 3. The guard walks the resolved spans in order and refuses atomically. Related: the trailing newline now follows the resolved span that reaches EOF rather than `hunks[-1]`, which was only "the hunk at EOF" when the patch happened to list hunks in file order.
57. **`patch`: empty lines separate hunks; a blank line inside a hunk is ` `, `+` or `-`** — an empty line belongs to no hunk, so the body run below it starts a new one, for any number of empty lines. The old parser filtered empty out before parsing, making them invisible rather than separating, so two headerless hunks split by a blank line merged into one and were refused. It works today only when every hunk carries an `@@` header, because the header closes the previous hunk -- a rule that held by accident, so it is now stated.
58. **Verify a format claim against the reference implementation before designing leniency around it** — the step that became 57 was originally scoped to accept a bare empty line as a blank *context* line, on the belief that real patches need it and that dropping one was the "too strict" problem. Measuring `diff -u`, `git diff` and `difflib` showed all three encode a blank context line as a single space and never emit a truly empty line inside a hunk; GNU patch's tolerance works only because it consumes exactly `old_count` body lines, the very mechanism step 2 gave up, and its price shows as `Hunk #1 succeeded at 1 with fuzz 2`. Adopting it here would have broken a patch with blank separator lines between hunks -- which applies correctly today -- to rescue a case that had never been observed. Both readings fail loudly, so the safe side is the one that keeps working patches working; the real cost was a diagnostic that printed a blank as an empty gap between backticks, and that is what changed.

59. **The screen's `~~~~~` fence is one language, paired by the CommonMark rule** — the value separators emitted by `chat/message/content/process/tool_call.py` and the tool-hint fences of `Process` (`process.py`) are the same code-block delimiter consumed by the fence state machine (`pattern_processing.patterns` `("~", …, code_fence)`), so they were unified at five tildes and the pairing rule replaced: a fence run closes the innermost open fence of the **same character and at least its length**; every other fence-looking run is literal text. The old rule closed only on exact equality and *pushed* every foreign run onto `code_fences` permanently, so run.py's `~~~~ stderr ~~~~` inside the `~~~~~text` hint block (or a `~~~`/``` ``` run inside any block) desynchronized the machine for the rest of the message — the confirmed cause of the garbled streamed tool output (P0 symptom c). Five tildes deliberately out-length the `~~~~` runs that tool arguments and tool output contain (4-tilde runs, incl. `~~~~ stderr ~~~~`, stay literal inside a value block). The formatter must emit an **even** number of separators (N arguments → 2N; `{}` → 0): the old one emitted 2N−1 and leaked the top-level `}` whenever the object closed with a key expected. Two accepted, documented limits: a value containing a >=5-tilde run at column 0 can close its own block early — no fixed-length fence can prevent that; a tool-call stream truncated mid-JSON leaves the last value fence unclosed. `Process` computes its hint fences once and prepends/appends them on **every** callback: `self.pos` indexes the assembled string, and a prefix that vanishes after the first callback shifts every later chunk boundary by the prefix length (measured: dropped text at each boundary). The LaTeX/`$` state machine was not touched (no symptom; unverified).

60. **`rename` never overwrites, and its dry_run is a validation, not a diff** — a `rename` whose target exists is a refusal, checked with `lexists()` so a *dangling symlink* at `new_path` counts as existing; the model must move or delete the conflict first, deliberately. Silent overwrite is the one outcome a destructive file tool must never produce, and "target exists" is the only question whose wrong answer here loses data. `dry_run=true` runs the *identical* validation (a refused rename is refused under `dry_run` too, tested) and prints the planned rename - it is NOT a pasteable unified diff like `delete_lines`/`insert_line` (28/44): a rename changes no bytes, so there is no content to diff, and pretending otherwise would imply the preview round-trips through `patch`. The tool covers directories (whole tree, atomic same-filesystem) and symlinks (moved as links) although the original draft said only "files": `mv` does, and a rename that refused directories would push the model into `run_command mv` and around the tool layer entirely - the layer that exists to keep destructive work sandboxed and `dry_run`-able; the Tool Comparison Matrix `rename` row was corrected to Directory ✅ to match the code, per the docs rule "where spec and code disagree, code plus tests are right". Bytes/line-endings/permissions are untouched by construction (the file is never opened; `os.rename` semantics, with `shutil.move` only as the EXDEV fallback). Missing target parent is an error naming it - no `mkdir` side effect; same-path (`abspath` comparison) and move-into-own-subtree are refused.

61. **The heredoc-pollution rule is retired: TRAPS #2 is a resolved trap, not a live one** — three docs (`TRAPS.md` #2, `CONVENTIONS.md` git conventions, this file's implementation note) stated that the `run_command` wrapper appends its trailer to the *last line* of the command, so a heredoc terminator "never sees" it and wrapper text lands inside heredoc content, making `git commit -F file` mandatory and heredocs forbidden. Measured against the code that ships: `wrap_script()` returns four lines — `STATE_HEADER`, the command, `ABSORB`, `TRAILER` — so the trailer begins a new line, bare, and the `ABSORB` comment absorbs a trailing backslash — and `run_command.py` passes `script_as_file=True`, so bash executes a file with stdin on `DEVNULL` and resolves heredocs from the script text, nowhere near the trailer. Re-measured over the real file-delivery path (14 checks, all pass): a heredoc whose delimiter is the command's last line writes byte-exact with no bash warning and no trailer in the file; `git commit` is clean three ways (`-m` with a real newline, `cat > f <<EOF` then `-F f`, and `-F - <<EOF`); `$()`, `<<-`, two heredocs on one command, nested heredocs, and a body line that *imitates* the trailer are all clean; and an export survives a trailing comment, killing the note's quieter half ("environment silently stops persisting"). The **control is the proof the mechanism was ever real and is now gone**: the old glued form `command + ";" + TRAILER` still pollutes the file and still draws bash's `here-document ... delimited by end-of-file` warning, exactly as `68cff03` describes — and that commit shipped `test_trailer.py` t3 (heredoc unpolluted) with t5 (control: the old glue fails), so the fix has been pinned by a green test since then. `git commit -F file` remains the house style — it keeps a multi-paragraph message out of shell quoting — but it is a style choice now, not a safety requirement, and the docs must stop justifying it with a bug the code no longer has. One genuine survivor, stated so it is not mistaken for the old trap returning: an **unterminated** heredoc still absorbs the wrapper into the file, because bash then reads to end of input looking for a delimiter that was never typed. That is malformed input and it warns loudly, so it is a footnote rather than a trap. The entry stays numbered 2 in `TRAPS.md` rather than being deleted: the numbering is positional and cross-referenced from `#3` onward, and a resolved trap is worth its space because the mechanism is one careless refactor away from coming back.

62. **`work.py` owns every line break of the assembled prompt** — the model is handed one string: `Work.prompt()` concatenates, per tool, `## <tool>` + PROMPT + PROMPT_INST (with `[placeholder]` settings substituted), wraps the result in `TOOL_PROMPT` and puts the chat prompt around that. The concatenation has two seams — a tool's own text into its instructions, and one tool's block into the *next* tool's `##` heading — and `f95aaa7`, which moved the separator out of run_command's PROMPT and into work.py (the right place), closed only the first. The second is the bigger one, and was invisible because nothing tested `prompt()`: measured on the real tool set, **1 of 19 headings started a line**, the rest arriving as `...using glob patterns.## get_current_weather`. In Markdown an ATX heading is a heading only at the start of a line, so the model was reading one run-on paragraph with `##` buried in it — the boundaries that tell it where one tool's contract ends and the next begins were not there. `prompt()` now builds one block per tool and joins the blocks with a blank line, `prompt_inst()` puts exactly one break in front of the substituted instructions, and both strings are stripped of surrounding newlines on the way in. The rule is that division: **structure belongs to the assembler, prose to the tool**, so neither PROMPT nor PROMPT_INST carries a leading or trailing newline and no tool author has to remember one — and a user setting saved under the old convention, which does end in `\n`, renders byte-identically to the same text without it instead of opening a blank line inside one tool's section. What the assembler deliberately does *not* own: the newlines inside a PROMPT_INST (python.py spells four instruction lines) belong to that string, and a PROMPT containing a `##` of its own still reads as a heading — nothing prevents it and nothing needs to. Pinned by `tests/unit/prompt/test_prompt_assembly.py` — 33 checks driving the real `prompt()` with httpx/Textual stubbed (TRAPS #19; no stub is ever called) over synthetic shapes *and* the real PROMPT/PROMPT_INST strings of every tool in the tree, read out of the sources with `ast` because importing a tool module needs the app's runtime — 10 of which fail against the pre-fix work.py. The two checks in `tests/unit/sandbox/test_prompt.py` t6 that pinned the *opposite* contract ("PROMPT must end with a newline, work.py joins with no separator") are re-pinned to the new one: a trailing break there would now reach the model as a blank line in the middle of a tool's section.

63. **The shell wrapper belongs to bash, so bash is the only one that gets it** — `8b505d1` tuned `run_script` in line with `run_command`: deliver the script as a file, accept a path where a script was expected, take a `separate_stderr` — and put `wrap_script()` in front of the script for *every* interpreter. `wrap_script` is not a neutral envelope, it is bash (`EXIT_CODE=${?}`, `export -p`, `pwd -P`), and the result is handed to whatever `interpreter` says. Measured on the file the tool really delivered: `python3` → `SyntaxError` on the trailer line, rc 1, and **no output from the script at all**, because python parses the whole file before executing any of it; perl the same (`Can't modify constant item ... line 1`, `syntax error at ... line 2`, rc 255). The model got a traceback quoting shell it had not written, for python3 and perl — the two interpreters, besides bash, that the tool's own default allowed setting names. 64. **`run_script` enforces its `interpreters` setting, and checks the name that was asked for** — the setting had exactly one consumer: substituting the `[interpreters]` token in PROMPT_INST. 66. **The terminal screen is cached in `app.tmux[chat_id]`, per session name, because nothing on the object survives a call** — `term_screen()` built the screen into a local and returned `self.output`, which was assigned exactly once, to `""` in `__init__`, so a live pane returned an empty tool response and a dead one returned `"\n\nINFO: Session dead."` with an empty prefix. The one-line fix (write the local into `self.output` before returning it) is correct and insufficient, and the reason is the interesting part: `spit_app/tools/terminal.py` constructs a **new `Terminal` inside `call()`**, so an instance attribute is born empty on every call and can only ever hold a screen captured earlier *in the same call*. That covers the input path — `term_send_keys()` captures before sending, so a session killed by its own input reports the screen just before — but not the case the dead-pane branch exists for: a session that died between two calls still answered with an empty prefix. 78. **The tool interpreter is `python3 -E -s -P`: the working directory and the environment are state, and CPython puts both of them on `sys.path`** — the reported symptom was a file tool answering with a traceback instead of a result, and with the file unwritten, naming a file in the venv: `write_file` dying inside its own `import pathlib` at `site-packages/textual/types.py` with `ModuleNotFoundError: No module named 'textual'`. The mechanism is not in the tool and not in the target file. A tool's program reaches python3 **on stdin** (`script_as_file` is False for the 13 script tools), and stdin mode puts `''` — the current working directory — **first on `sys.path`**; the working directory is *state*, because `run_command`'s `cd` carries over to the next call. So a call that ended inside a python package directory left every later file tool importing that directory in place of the standard library, and any module name in it that the tool's own import graph reaches (`pathlib → glob → contextlib → functools → types`) resolves there. Which tool died was decided by that graph and never by the file being edited: measured in the same poisoned directory, `read_files.py` (which imports nothing) answered normally while `search_replace.py` (`re → enum → types`) did not — which is the whole of the "intermittent", and it lasts exactly as long as the shell sits in that directory. The second door is the other half of the state: one call exporting `PYTHONPATH` pointing at a directory holding a `types.py` poisons the next tool call with the working directory perfectly clean.
    **`TOOL_PYTHON` closes both doors** — `-P` keeps the interpreter's start-up directory (the cwd in stdin mode, the script's own directory in file mode) off `sys.path`, `-E` keeps the inherited environment off it, `-s` keeps user site-packages out of a script that is pure stdlib by rule (TRAPS #19). `-P` is 3.11+ and `-I` has meant `-E -s -P` since 3.11; the repo is built and tested on 3.13, and the three are spelled out rather than collapsed into `-I` because they are three separate reasons. `Run` now takes an interpreter with arguments of its own (`cmd: str|list`, `self.cmd = list(cmd) if isinstance(cmd, (list, tuple)) else [cmd]`), so `run_command`'s bash and `run_script`'s chosen interpreter keep the one-word form and nothing else about the delivery changes.
    **What the rejected alternative would have cost, and why it is rejected.** The proposal on the table was: let only `run_command`, `run_script` and `terminal` load `~/.sandbox_env`/`~/.sandbox_cwd`, and run the other tools without the state. Measured, it does silence this crash — and it is not the fix, for four reasons. **(a)** It leaves `sys.path[0]` pointing at a directory anyone can write into (the sandbox home): remove the trigger, keep the mechanism, and the next stray `types.py` in `~` reproduces the identical failure. **(b)** The premise that the file tools do not depend on the state is false for the cwd half.     **(a) THE NOTE LIVES UNDER A PRIVATE KEY IN THE MESSAGE DICT — NOT AS A MESSAGE.** The constraint came from the owner and it is the one that decides everything else: a note may not become an item of `chat.messages`, because that list is the **UI's index space**. The sliding window projects it by dict identity (`window_consistent()`, DECISIONS 76), `StreamCallback` and `RemoveMessage` carry indexes in their bodies, `Undo` stores them, and a mid-stream `ToolCall`/`LlamaCppEndpoint` holds a `message_index` into it (P13's constraint paragraph). A note inserted in the middle of that list while a stream runs renumbers every one of those — that is the bug, not the feature. So `SystemNotes(chat).attach()` writes `{"hook", "level", "text"}` into `messages[index]` under `NOTE_KEY = "system"` and never touches the list (`spit_app/chat/system_note.py`), and `endpoints/llamacpp.py:prepare_payload()` pops the key from the **deepcopy** it already makes (the same loop that renames `reasoning`), so the wire never sees the private key and the stored dict keeps both its note and its own content byte-identical. Pinned from both ends: generator t5 (list object identity, length, per-message `id()`, every other key unchanged), generator t7 (the stored shape is dicts, not namedtuples — a namedtuple would persist as a JSON list), endpoints t12 (`t12-key-set-of-every-wire-message-has-no-private-system`, and the app-side copy asserted unchanged), endpoints t13 (the UI's `chat.messages` grows by the streamed replies only, no note ever becomes an item, `ChatView` still projects the same list object). The word *system* in the key names what the note is **for** — a message to the model, in ordinary language — while the ROLE it ships under is `user`, which is (c); the two spellings are deliberate and greppable, not a leftover.

    **(b) ONCE, AT THE TAIL — BECAUSE A NOTE THAT IS TRUE STAYS TRUE.** The generator asks at every message index (generator t2), and `TokenStatus.notice()` answers at none of them except the last (the `index != len(messages) - 1` early return; hook t11 tail-only): a note is written at the moment it becomes true and from then on it is history. The reason is the prompt cache — llama.cpp's automatic prefix cache and this app's own `/slots?action=restore` (`endpoints/manage_cache.py`): a note re-injected at a moving position, or hoisted into the leading system prompt, changes text the server has already prefilled and costs the whole cached prompt on every request. **WP-A corrected this entry's first draft on the cost of the merge, and the correction belongs here**: prefix caching is positional, so a note merged into the content of the message that carries it invalidates only that message's tokens — one tool result, usually — not the prompt; what genuinely invalidates is rewriting position 0 or moving a note that is already in the history. So the once-at-the-tail rule stands for the reason it was drawn (a note never moves), and the merge rule of (c) costs a message, not a prompt. Pinned by generator t3 (a written note is history: a re-run of the same walk adds nothing), endpoints t13 (`t13-the-old-note-still-rides-in-its-own-history-position`, `t13-same-level-second-request-adds-none`), and endpoints t12's merge cells.

    **(c) THE ROLE IS `user`, NEVER `system` — AND THE RULE THAT KEEPS `user` LEGAL IS A MERGE (owner ruling, 2026-09-25).** A mid-conversation `system` message is not merely unusual, it is refused outright by strict templates: the Qwen3.x template in llama.cpp carries `{{- raise_exception('System message must be at the beginning.') }}` (`models/templates/Qwen3.5-4B.jinja`, line 85) and the server answers **400/500 for the whole request** — not a degraded reply, no reply. The same wall is reported in llama.cpp #27367, #20733, #18895 and QwenLM/Qwen3.8 #244, all of them agent harnesses injecting mid-conversation context exactly like this one; their workarounds are hoisting into the leading block (which is (b)'s cache-breaker and puts the note in the one position that must stay stable) or shipping a patched template (a fix in a file this repo does not own). The owner's ruling replaces both: **notes ride the wire as `user`** — and the proof it works is not the OpenAI contract but their own hands, months of abort → type *"You have 10k tokens left. This is critical. Write a fenced handoff message NOW!"* as a user message after the tool result → continue inference. `user` after a `tool` message is legal because the grammar every tool-capable template implements is `assistant(tool_calls)` → `tool`* → anything: the `tool` run ends at the first non-`tool` message, and a human turn closing it is the ordinary next turn. What `user` costs is the **other** family's rule — mistral-instruct and gemma-it `raise_exception` on two consecutive `user` messages ("Conversation roles must alternate…"), and a `user` note creates exactly that pair whenever its carrier is itself a `user` message (the first send of a chat, or `action_continue` on a user message). |---|---|---|---|---|
| 32k | 50 % (16.4k) | **39 %** (12.8k) | **69 %** (22.8k) | the floors |
| 64k | 50 % (32.8k) | **69 %** (45.5k) | **85 %** (55.5k) | the floors |

    **The consequence is a design rule, not a wart**: on a small window a HIGHER-ranked level triggers at a LOWER fill than a lower-ranked one (32k: `warning` at 39 %, `info` at 50 %). So the verdict is the highest level whose trigger holds, and it is announced only if its rank is strictly above every rank already announced — `LEVELS` is ordered critical→warning→info and `announced = max(rank of own standing notes)`, never "whatever threshold was crossed last". On a 32k window the first note the model ever sees is `warning` and `info` is **shadowed forever**; that walk is pinned exactly (`t14-order-32k`: `small_window, warning, critical`, `t14-info-is-never-emitted-on-a-32k-window`), and testing the levels in trigger order reddens 31 checks. 84. **A failure carries its status, the retry wraps only the request, and the rollback keeps the queue's order** — P19/WP-2 on `task-endpoint-retry-p19wp2`; the three open decisions of the P19 entry, taken, plus what measuring the first shape of the loop changed. `unit:endpoints` 442 → **512** (t14's 69 checks new; t6 re-pinned in place, its two checks moved with the behaviour and its count up by one), every other row at the `doc/TESTING.md` numbers, `chat_smoke`'s golden md5 `8ae9d1186a59627d30d05dee95f0ad95` unmoved.

Attempts count **requests**, so 1 is "no retry" and the default 3 is the owner's "at least 3 times". Both join `Endpoints.NEW` and `construct_payload`'s skip list (a client-side fact forwarded to the server is a request the server refuses — t5's deliberately leaking `n_ctx_control` 4242 is the control that proves the leak, and t14 puts it in the same payload), and both are read through `setting_value()` with a default, because the settings file is read verbatim and no migration was authorised: every endpoint saved so far lacks both keys and must answer 3 / 1.0, not raise KeyError. A blanked field (the shape `store_values` leaves, `value: None`) answers the default too, and t14 pins all three cases.

    **(b) AUTO-SUBMIT the recovery chat when the probe answers, DRAFT when it does not** (WP-4 builds it): the probe is `get_models` at `timeout=3`, the same question the counts row already asks. Reachable ⇒ submit and let the agent run, because the owner's complaint is that a failure "needs human intervention"; unreachable ⇒ the brief goes into the new chat's text area as a ready draft and the chat says so, which still beats a modal that halts — and a submitted message into a dead endpoint is a second failure with the human's words inside it.

    **(c) The modal `ErrorScreen` stays for a deterministic 4xx; transient and exhausted failures become an in-chat notice** (WP-4 builds the notice). A 400 the app cannot fix is a real user error and a dialog is the honest way to stop and say so. The modal that blocks EVERY chat is a large part of why a failure feels like a halt, so it must not be what a rate limit or a dead socket produces.

    **(d) THE WIDTH OF THE LOOP IS THE DESIGN, and one attempt is not one POST.** `stream_attempts()` loops around `attach() + endpoint.stream()` and nothing else: `work_stream()` runs the tools BEFORE the request and recurses AFTER it, so a loop around anything wider re-executes every tool call — files already written, commands already run — on each attempt. Non-`EndpointFailure` re-raises out of the worker (a bug elsewhere is not retried) and the `finally` still returns the slot. What the checks count is therefore TWO numbers: `attempts_of` (requests carrying no `stream_options`) and the POST count, because `stream()` probes `stream_options` and re-sends without it on any 4xx (t6's rule, untouched), so **one 4xx attempt is two POSTs** and a check that expected 1 wherever the wire says 2 would pass on a loop that retried twice and never asked about the flag. On a 5xx the probe never runs and the two numbers agree: a 503 costs exactly `retry_attempts` requests, measured at 1, 2, 3 and 5.

    **(e) ONE rollback, reached through the queue, and an undo entry per attempt.** `ChatView.remove_message_at` is now the single removal body and `on_remove_message` is a thin awaiter of it, so the undo record, the widget under its own lock, `window_start`, the data delete, `write_chat_history()`, the ONE focus rule and `is_removing` cannot drift between the user's remove and the retry's. The first shape AWAITED it from the work loop between attempts, and that crashed: `stream()` posts its own `StreamCallback`s on the ChatView, so a dead attempt leaves signal 1 in that queue, and deleting the data around the queue lets the queued signal mount an index one past the end (`_grow_down` → `IndexError` out of a Textual message handler — the app dies, with the retry). `Work.roll_back_attempt` therefore POSTS and waits for the data to move, using the view's own `is_removing` handshake (which also holds prune off and stops a second remove posting behind it); the queue is FIFO, so the removal runs after the signals of the attempt it is cleaning. Bounded, and a rollback that never lands releases the flag — a held `is_removing` would keep prune away for the chat's whole life — and the loop reports instead of stacking a reply on a corpse. The accepted cost: **each rolled-back attempt records its own undo entry**, so undoing after three failed attempts walks back three identical removals; the alternative was a rollback that skips the undo record, i.e. the second removal path this package exists to remove.

    **(f) THE STALE SIGNAL IS A HOLE WP-2 FELL INTO, and it predates WP-2.** `action_abort` deletes the streaming tail by DATA index without waiting for the queue, so a signal for a dict that no longer exists has always been reachable; the awaited rollback made it reproducible. `CallbackMixIn.on_stream_callback` now drops a signal whose index is not a message. A live reply cannot match the guard — signal 1 is posted immediately after `messages.append(...)` and 2 and 0 while that dict stands — and t14-G pins both sides, the silence with the control that a live index still gets its widget.

    **(g) ABORT KNOWS A RETRY SLEEP FROM A TOOL CALL.** `action_abort` branched on `busy`, which is True only around a tool call, so Ctrl-C during the delay took the cancel-and-delete branch and `messages[-1]` was by then the HUMAN's own turn: abort deleted the message the user just wrote. `Work.retrying` is True exactly in that delay and the test is `busy or retrying`; the sleep runs in 0.1 s slices on that flag and `exit_after_busy`, so an abort costs no further request and ends within about a tenth of a second (measured against a 5 s delay). It is SILENT — an abort is not a failure.

    **(h) The classification lives in the endpoint, and `str()` did not move.** `EndpointFailure(status_code, retryable)` with `TransientFailure` / `ConnectionFailure` / `StreamFailure` / `DeterministicFailure` / `ContextLengthExceeded`, built by `refusal_failure()` / `stream_failure()` / `transport_failure()`; `stream()` turns the whole `httpx.TransportError` family — the five the old name-tuple listed by hand — into one `ConnectionFailure` `from` the httpx error, and `CancelledError` is deliberately not caught: an abort must not be relabelled as a failure. The user-facing sentences are byte-identical to what the app always showed (`Endpoint returned {code}: {text}`, `Endpoint raised Error: {code}, Type: {typ}, {message}`), pinned at `test_requests.py:76`/`:90` and again in t14; what moved is the TYPE, which is what t6's two re-pinned checks now say. `ContextLengthExceeded` is named because on an endpoint that answers neither `/props` nor `/slots` the 400 IS the first signal (80 b, 81 d) — and the dash stays a dash: nothing here guesses a window to make the notes fire.

85. **The journal is an in-process tool, its cap is a ceiling on the READ and on the read only, and the cap is read from the app rather than from the module** — P19/WP-3 on `task-endpoint-retry-p19wp2`; the owner's second half of the failure-recovery brief ("a new tool the agent can use while still alive to keep records — a kind of journal — which then becomes the recovery message in the new chat"). New `spit_app/tools/journal.py`, new `unit:journal` **69** (t1–t8), `unit:prompt` 33 → **38** by added checks, `unit:system_note` **219** with its two texts re-pinned in the same commit as the change, every other row at the `doc/TESTING.md` numbers, `chat_smoke`'s golden md5 `8ae9d1186a59627d30d05dee95f0ad95` unmoved.

    **(a) IN-PROCESS, NOT A `scripts/` TOOL — and the reason is checkable, not stylistic.** `bwrap_args()` binds `app_home/sandbox` over `/home/<user>` and `sandbox_tmp` over `/tmp`, so the app's data dir is **not a path a sandboxed script can reach**; a script tool could write its records only somewhere the recovery could not read them back, which is the whole point of a journal. So it is `call(app, arguments, chat_id)` — `set_chat_description`'s shape — and t1 pins both halves of the claim: that no `scripts/journal.py` exists, and that `tools/run/common.py` really does override the homes. It is a **plain `def`**, not `async def`, and that is DECISIONS 68 applied rather than a preference: `ToolCall.call()` runs a plain function through `asyncio.to_thread`, so the disk I/O happens off the event loop; the two async in-process tools are async because they mount and focus widgets, and this one touches nothing but the data dir.

    **(b) THE CAP IS ON THE READ, NEVER ON THE JOURNAL, AND IT CUTS AT AN ENTRY BOUNDARY.** One file per chat, append-only, one entry = a marker line + a **multi-line** body + a blank line, so the fields a record of work has (`Branch / Scope / Done / Left / State hazards / Verify`, the `TASKS-IN-PROGRESS.md` shape that has carried this repo across three crashed sessions) are **one** entry and not five, and a body line that opens with `[` is body. `journal_max_chars` (default 4000) exists because the tail of a journal is destined for a **fresh chat's** context on the recovery path — the one place the room is scarce — which is the same reasoning that caps a dead terminal's report at 50 lines (69 d). Two consequences, both pinned: what a cap cuts is **still in the file** and the answer says so, and a cap **smaller than the newest entry shows that entry whole** — the newest record is the one a successor must never be handed in halves, because a truncated record is indistinguishable from a complete one to a reader who was not here. The setting answers the **module default** for a blanked field, a string, zero, a negative, a bool and a float: the field is a `uinteger`, and truncating `1.5` to `1` would be a cap that reads almost nothing — a policy nobody asked for.

    **(c) THE CAP CAME OUT OF MODULE STATE, AND THAT IS THE HAZARD WP-3 FOUND.** The house pattern is `load_user_settings(app, NAME, SETTINGS)`, which **copies the user's values INTO the module dict** — and that dict is shared by every chat in the process. Reading the number back out of it after some other chat's call is reading **that chat's** value: measured, a chat whose cap was 300 left the next chat, which has no saved cap at all, reading 300 too. `effective_cap(app)` reads the setting where it lives, with `MAX_CHARS` behind it for a settings file written before the tool existed; the `load_user_settings` call stays because the PROMPT needs it. The same trap is one grep away in every other in-process tool that reads a numeric setting back out of `SETTINGS` after that call — recorded here rather than fixed, because changing another tool's behaviour is not WP-3's concern (filed in the task entry).
    **(d) A CHAT ID BECOMES A FILE NAME, SO IT IS WHITELISTED.** The first draft refused `""`, `/` and `..`; `a\b` walked straight through. A blacklist has to be right every time and a whitelist once, so the id must match `[A-Za-z0-9_-]+` — what this app's ids are — and anything else is a refusal that writes nothing, with the control that the same call with a good id does write (t8). A refusal also creates no `journal/` directory: the absence is asserted, so a "refusal" that half-wrote cannot pass.
    **(e) THE TWO NOTE TEXTS AND THEIR RE-PIN ARE ONE COMMIT, AND THE JOURNAL IS NEVER THE RECOVERY'S ONLY SOURCE.** `TEXT_WARNING` and `TEXT_CRITICAL` each gained **one** clause — write a journal entry now, and on `critical` *before* the handoff — with their `t16` pins re-worded in the **same commit**, the ruling-iv precedent of 82 (model-facing text and the checks that quote it move together, never a window where a green suite pins a text the app no longer says). The load-bearing half of `critical` — *do not call any more tools and do not start new work after the handoff* — is byte-identical, and the `warning`/`critical` mechanisms of 81 are untouched. Both clauses say **"if the … tool is available"**, because existing chats gain no tool retroactively (82 d). And the journal may never be load-bearing for a recovery to exist (the P19 entry's alteration 3): a chat that never wrote one still gets the app's own brief, which is why the tool's own answer to an empty journal is a sentence about that and not an error.

86. **The recovery is a message in a new chat, the notice is a message in the old one, and the chain is one deep** — P19/WP-4 on `task-endpoint-retry-p19wp2`; the wiring the other three packages were cut for. New `spit_app/chat/recovery.py`, `create_and_submit`'s `submit=` switch, `Work.report_failure` async with the attempt number, new `unit:recovery` **55**, every other row at the `doc/TESTING.md` numbers, `chat_smoke`'s golden md5 `8ae9d1186a59627d30d05dee95f0df0ad95` unmoved.

    **(a) THE NOTICE IS A `role: "user"` MESSAGE, appended through `Chat.action_add_image`'s shape — and its cost is stated, not hidden.** Two shapes were on the table: a message, or a notice widget of the ChatView's own. The widget was rejected: the sliding window's invariant is that the mounted children are exactly a slice of `messages`, and a widget that lives in the view without being in the data is a second thing the window arithmetic has to know about, plus CSS, plus the focus rules — for a fact that disappears on reload. The message needs none of that: append the dict, `write_chat_history()`, post signal 1 and signal 0, and every handler the human's own submissions already go through does the mount, the undo record, the write and the finish. It survives a reload because it IS the transcript. **The honest cost: the notice rides the next request if a human continues that chat** — the successor model reads it as something the user said. That is accepted because the alternative is worse in kind: a modal that halts every chat, or a fact nobody can see after a restart. The two ways this could be written wrong are pinned: the `user` role is what `action_add_image` uses and the window invariant check (`t6`: `window_consistent()` AND the notice has a widget) is the pair that would fail on a view that mounted nothing at all.

    **(b) `report_failure` IS ASYNC, and the fallback to the old report is the load-bearing part of the change.** It mounts widgets now, so it is `async def` and takes the attempt number the brief quotes. A `DeterministicFailure` keeps the old report byte-identically — the modal, the corpse taken back, the model list refreshed — because a 400 the app cannot answer for is a user error and the honest thing is to stop and say so (84 c). A transient or exhausted failure asks `recovery.recover()` first, and on a True answer does not set `app.exception`; on **any** exception, or a False, it falls through to the same old report. That fallback is what keeps `unit:endpoints` at **512 unchanged**: the suites that drive `Work` on a bare `StubSettings` have no settings home to write a chat into, so `can_recover(app)` answers False **before** the probe — no request spent, no sleep, no message, no undo entry, and `t14-A`'s CONTROL (no corpse), `t14-B`'s exhausted-`StreamFailure` report and `t14-D`'s `["remove"]*3` all stay exactly as they were. A recovery whose own gate is honest cannot corrupt a suite it was never meant to run in; a recovery that swallowed its exceptions in a different place could. `DeterministicFailure` therefore joins `stub_modules.py`, since `work.py` imports it at module level and `unit:prompt`'s bare interpreter dies on a name that is not stubbed. The recovery module itself is imported INSIDE `report_failure` — at module level it would pull `chat.handoff` → `chat.chat` → Textual into `work.py` and kill that suite outright.

    **(c) ONE probe, and it is the question the counts row already asks.** `get_models` at its own `timeout=3`, answering `[]` on any failure — reachable ⇒ `create_and_submit(..., submit=True)`, unreachable ⇒ the same call with `submit=False`, which does everything except the `action_submit()`: the brief lands in the new chat's text area as a draft for a human (84 b). No new timeout plumbing because there is nothing new to time out on, and the answer is carried out of the one call rather than asked again for the notice's wording — a second probe could be answered differently and would say the opposite of what was done. The two branches are distinguished by what a stopped server makes unmissable: with the server refusing replies the brief is recorded as a POST body (`t1`), with the server stopped it is nowhere on the wire (`t4`), and the same marker is the evidence in both.

    **(d) `recovered_from` IS A `csettings` ENTRY, so the provenance and the depth cap are the same fact.** The continuation chat inherits the dead chat's `csettings` whole with exactly two differences: `desc` becomes `"Recovery: …"` keeping its entry shape, and `recovered_from` is added as `{"value": <the old id>, "stype": "string", "desc": "Recovered from"}`. It round-trips verbatim through `write_chat_history()` and the manage screen renders it as a field like any other — visible to the human, readable by the code. The depth cap is one: a chat whose own `recovered_from` is truthy **reports, it does not recover** — the notice says the chain ends. Without it a dead endpoint spawns one chat per failed request forever, each inheriting the same dead endpoint, which is the hazard the P19 entry's alteration 2 named. The suite proves it as a fact about the world rather than a branch: `t1`'s continuation chat is submitted into the same refusing server, so it really fails, reaches the recovery, and `t2` waits for THAT notice before counting the chat files (two). Reading the flag goes through `csettings.get("recovered_from", {}).get("value")` and not `Chat.cs()`, which RAISES `KeyError` on a key the chat file never had.

    **(e) THE JOURNAL IS APPENDED WHEN THE FILE EXISTS, AND NEVER AS A SENTENCE ABOUT ABSENCE.** `journal_part` checks `journal_path(...)` and its `.exists()` and, when there is no file, writes its own line; it does not paste `read_journal`'s answer, because that answer is a paragraph ADDRESSED TO THE AGENT who would write one and inside a brief it reads as a journal whose entries are advice. `journal_max_chars` therefore never appears in a brief for a chat that kept none — pinned next to the case where a journal written by the REAL `journal` tool rides the brief with its `Journal of <id>` header (`t5`/`t5b`). The brief's fields are all things the app holds: the dead chat's id, the path `chats/<id>.json` (`read_files` can read the whole thing), the failure with its class and the endpoint's own text, the requests it took, the token counts, the last ten turns at 400 characters each with the cut marked, and the closing "Continue the work." — no invented summary of what the chat was about, which the app was not there for. And the recovery bypasses `ToolCall` deliberately (82 d): behind the `handoff` tool it would be missing exactly where it is needed — the chat that never selected that tool, and the request that died rather than the tool loop.

    **(f) THE ORDER THE CORPSE GOES BACK IS NOT A TIDY-UP.** `report_failure` removes the failed attempt's dict with the awaited rollback BEFORE the recovery reads or writes a message. Two things downstream touch the tail: the brief quotes the transcript (a corpse would be quoted at a successor as if it were a reply), and the notice is APPENDED — and the removal's index is `len(messages)-1`, so a removal posted after the append would take the NOTICE back and leave the corpse standing in the dead chat forever. Same rollback as the retries, one seam, reached the same way (84 e).

## Implementation notes (verbatim)

- Avoid doc strings `""" ... """` and comments `# ...`. If possible write code so it can be easily understood (the code should be the doc!). Don't use syntax constructs that are difficult to understand or read. Use methods with descriptive names instead of comments or doc strings. Simplicity is far more important than ingeniousness. Easy to read code is doc that's always up-to-date.

- **Python environment gotcha (verified 2026-08-19)**: the app's dependencies (`libtmux`, `textual`, ...) are **NOT installed in the bare system `python3`** (`/usr/bin/python3`, 3.14.6) — `find / -name "libtmux*"` finds nothing, `python3 -c "import textual"` fails, and there is no `~/.local/lib` or venv in the home directory. The app's real runtime is separate (recent `cpython-313`/`cpython-314` `__pycache__` entries prove the app runs with deps available elsewhere — likely a container). Practical consequences when testing:
  - **Tool scripts** (`spit_app/tools/scripts/<tool>.py`) are self-contained pure-stdlib and do not import app modules — test them directly with the system `python3` by prepending an args block and piping via stdin (exactly how `Run` does it). See `spit_app/tests/tools/harness.py` for the shared test driver.
  - **Tool modules** (`spit_app/tools/<tool>.py`) import `Run` from `spit_app.tools.run.run` to verify DESC/SETTINGS/EXEC wiring:
    ```python
    import sys
    from spit_app.tool_call import load_module_from_path
    from pathlib import Path
    m = load_module_from_path('tools.<name>', Path('spit_app/tools/<name>.py'))
    print(m.DESC['function']['name'], m.EXEC['interpreter'], len(m.EXEC['script']))
    ```
- All tools run in sandbox (`bwrap`) for security
- Error handling is comprehensive (FileNotFoundError, PermissionError, etc.)
- Human-readable output formats (sizes, dates, permissions)
- Markdown rendering for better readability in chat
- If the tool does not output Markdown, set `OUTPUT_TYPE_HINT` in the tool's module. You may set it to 'text', 'python', 'json', or similar, so the output is not interpreted as Markdown on screen. The actual tool output remains untouched and will be fed to the LLM as is. `OUTPUT_TYPE_HINT` only changes the rendering on screen for the user. 
- Shared utility functions between tools (de-duplication)
- `dry_run` parameter for all destructive operations
- Preview before applying changes
- Per-tool test directories are in `spit_app/tests/tools/<tool_name>/` and contain **exactly three files**: `setup.json` (script path + arg names, optional `common`), `run_tests.sh` (shared `harness.py` + `test_common.sh`) and `create_fixtures.sh` (shared `fixtures_common.sh`). Fixtures are **never stored**: `run_tests.sh` runs `create_fixtures.sh`, which writes `./fixtures/` with `testfile`, and removes the directory on exit (`KEEP_FIXTURES=1` keeps it). Nothing byte-sensitive is in git, so no transport can rewrite the line endings a test depends on, and a run leaves no scratch behind anywhere
- **Fixtures are named after the test that owns them** — `fixtures/tNN-<short-name>.txt` (scratch and must-not-exist paths too), `shared-<name>` when several tests read the same content, `corpus/<name>` for `patch`'s corpus. A `tNN-*` file is read by test `NN` only; that rule exists because a test comparing against another test's expectation passed twice before the names made it impossible (decision 49). `create_fixtures.sh` is in test order and holds only `testfile` lines. **Nothing a run touches lives outside `./fixtures/`** — no `/tmp` paths in any suite
- **`grep` matches per line** (`regex.search` on each line) — simpler and more predictable than whole-file multi-line matching; file discovery uses glob `file_pattern`, output is sorted for determinism
- **`grep` output uses standard grep separators** — match lines `path:line:`, context lines `path-line-`; context ranges are merged when overlapping/adjacent so context lines are never duplicated
- **`grep` is lenient about `path`** — the spec says directory, but a single file is accepted and searched on its own; binary/unreadable files are skipped with a count note; missing path / invalid regex are errors (non-zero exit), zero matches is NOT an error (exit 0, consistent with `diff`)
- **Test harness flags are read once** (`sys.argv.index`) — passing the same `--flag` twice silently uses the **first** value, so a test must pass the complete arg set on every call rather than appending overrides to a shared base string. `tests/tools/delete_lines/run_tests.sh` wraps this in a `dl PATH START END PATTERN DRY` function so no flag is ever repeated.
- **A `dry_run` preview that is documented as pasteable into `patch` needs a round-trip test** — extract the diff from the preview (awk from `^--- ` to the summary line), apply it with the `patch` harness, and compare against the file the tool itself produced. That is exactly how the missing `\ No newline at end of file` markers in `delete_lines` were caught; its suite covers blank-line, no-trailing-newline, CRLF, whole-file and scattered-pattern shapes this way.
- **Whole-line destructive tools read and write with `newline=''`** — Python must never re-translate line endings on its own; combined with `splitlines(keepends=True)` this makes LF/CRLF/lone-CR handling a non-issue for line-based tools (`delete_lines` needs no terminator detection at all).
- **A tool whose script is assembled with `get_script(__file__, "<common>")` needs a `"common"` entry in its `setup.json`** — the harness reads the raw tool script, so without it the whole suite dies with `NameError` on the first missing shared helper. `insert_line`, `patch` and `delete_lines` all point at `../../../tools/scripts/common/lines.py` now.
- **Terminator policy per tool (the last dedup is now done)**: `patch` and `insert_line` normalise to the terminator of the file's first line break (they must agree, or an insert and its own preview patched by `patch` give different bytes); `delete_lines` keeps every remaining line's exact terminator and needs no detection, because deleting never rewrites an untouched line. That last dedup is **done** (branch `delete-lines-shared-line-helpers`): `delete_lines` calls `strip_newline()` / `read_text_raw()` / `write_text_raw()` from `common/lines.py` and keeps its own policy, so the primitives exist once and the per-tool rules above are still three lines of difference, not three copies of the same code.

- **`patch` placement contract** (decisions 53-57): body is ground truth, header is a tie-breaker, a tie is refused, every hunk is matched against the pre-patch file, empty lines separate hunks. The tool keeps no line counts at all — `old_count`/`new_count` were deleted once the trailing-newline decision moved to resolved spans.
- **Prove a behaviour change by differential against the previous version over every fixture, not only by the suite** — group results by (old verdict, new verdict) and assert that nothing which applied before applies *differently*. A green suite cannot see a refusal that became an application, and this series deliberately changed many of exactly those.
- **Test numbers are append-only.** Freed numbers (5-9 in `patch`) are not reused, so `tNN-*` keeps one meaning across the history of a suite.
- **Before writing leniency into a parser, measure the reference implementations** (`diff -u`, `git diff`, `difflib`, GNU `patch`) and record what each actually emits. See decision 58.
